# Технический отчет: Расчеты и конфигурация запуска HauhauCS Qwen3.8-27B Aggressive MTP (Q5_K_P) на Tesla V100 32GB

**Модель**: [HauhauCS/Qwen3.8-27B-Uncensored-HauhauCS-Aggressive-MTP-GGUF](https://huggingface.co/HauhauCS/Qwen3.8-27B-Uncensored-HauhauCS-Aggressive-MTP-GGUF)  
**Целевой квант**: `Qwen3.8-27B-Uncensored-HauhauCS-Aggressive-Q5_K_P.gguf` (20.22 GB / 18.83 GiB, 5.92 BPW)  
**Спекулятивное ускорение**: `Qwen3.8-27B-Uncensored-HauhauCS-Aggressive-FastMTP-32K.gguf` (903 MB / 0.84 GiB)  
**Мультимодальный проектор**: `mmproj-Qwen3.8-27B-Uncensored-HauhauCS-Aggressive-BF16.gguf` (931 MB) — **строго в CPU RAM**  
**Аппаратная платформа**: NVIDIA Tesla V100 32GB (SXM2 / PCIe, архитектура Volta `sm_70`, 900 GB/s HBM2)  
**Операционная система**: Debian 12 (Bookworm) x86_64, headless  

---

## 1. Архитектурный анализ модели Qwen3.8-27B

Модель Qwen3.8-27B построена на гибридной архитектуре внимания, сочетающей линейные рекуррентные слои и классическое разреженное внимание:

* **Общее число слоев (`num_hidden_layers`)**: 64
* **Скрытая размерность (`hidden_size`)**: 5 120
* **Размерность промежуточного FFN (`intermediate_size`)**: 17 408
* **Размерность головы внимания (`head_dim`)**: 256
* **Число голов внимания (`num_attention_heads`)**: 24
* **Число KV-голов (`num_key_value_heads`)**: 4 (Grouped-Query Attention с фактором 6:1)
* **Интервал полного внимания (`full_attention_interval`)**: 4
  * **48 слоев** используют линейное рекуррентное внимание (**Gated DeltaNet** / SSM) с константным размером памяти $O(1)$ относительно длины контекста.
  * **16 слоев** (каждый 4-й слой: 4, 8, 12 ... 64) используют стандартное внимание (**Gated Attention**) с классическим KV-кэшем $O(N)$.
* **Нативное контекстное окно (`max_position_embeddings`)**: **262 144 токена (256K)**.
* **Размер словаря (`vocab_size`)**: 248 320 токенов (draft-сайдкар FastMTP триммирован до 32 768 токенов).

## 2. Математический расчет емкости KV-кэша Q8_0

В гибридной архитектуре Qwen3.8 KV-кэш выделяется **только для 16 слоев полного внимания**:

### 2.1. Расчет элементов на один токен
$$\text{Элементов на токен на один слой внимания} = 2\,(\text{Key} + \text{Value}) \times 4\,(\text{KV-головы}) \times 256\,(\text{head\_dim}) = 2\,048\text{ элементов}$$
$$\text{Элементов на токен по всем 16 слоям внимания} = 16 \times 2\,048 = \mathbf{32\,768\text{ элементов/токен}}$$

### 2.2. Расчет байт на токен для квантования Q8_0
В библиотеке `ggml` блок квантования `Q8_0` упаковывает 32 весовых значения:
* 32 элемента $\times 1$ байт (int8) = 32 байта;
* 1 масштабирующий коэффициент (scale) в формате FP16 = 2 байта;
* Итого на блок из 32 элементов: 34 байта.

$$\text{Байт на элемент} = \frac{34}{32} = 1.0625\text{ байта/элемент}$$
$$\text{Расход памяти на 1 токен} = 32\,768 \times 1.0625 = \mathbf{34\,816\text{ байт/токен}} = \mathbf{34.0\text{ KiB/токен}}$$

В гигабайтах (GiB, $1024^3$ байт):
$$\text{Коэффициент памяти KV} = \frac{34\,816}{1\,073\,741\,824} \approx \mathbf{0.000032425\text{ GiB/токен}}$$

## 3. Бюджет памяти Tesla V100 32GB и базовый оверхед

### 3.1. Доступная память
* Физическая емкость HBM2: $32\,768\text{ MiB} = 32.00\text{ GiB}$ ($34.36\text{ GB}$).
* Доступно в Debian 12 (headless, без X11/Wayland, ядро + драйвер NVIDIA): $\approx \mathbf{31.60\text{ GiB}}$ ($32\,358\text{ MiB}$).

### 3.2. Базовые компоненты (Static Footprint)
1. **Базовая модель `Q5_K_P`**:
   * Размер файла: $20.22\text{ GB} = \mathbf{18.83\text{ GiB}}$ ($19\,282\text{ MiB}$).
   * Все 64 слоя загружаются в GPU (`-ngl all`).
2. **Сайдкар HauhauCS FastMTP-32K (`Qwen3.8-27B-Uncensored-HauhauCS-Aggressive-FastMTP-32K.gguf`)**:
   * Размер файла: $903\text{ MB} = \mathbf{0.84\text{ GiB}}$ ($861\text{ MiB}$).
   * Загружается в VRAM (`--spec-draft-ngl all`), ускоряя генерацию на 20–35% по сравнению со стандартным MTP.
3. **Состояние драфт-модели FastMTP (глубина depth=3, KV-буфер драфта)**:
   * $\approx \mathbf{0.08\text{ GiB}}$.
4. **Рекуррентное состояние 48 слоев Gated DeltaNet (константа $O(1)$)**:
   * $\approx \mathbf{0.35\text{ GiB}}$.
5. **CUDA Runtime & Driver Context**:
   * $\approx \mathbf{0.45\text{ GiB}}$.
6. **Scratch-буферы графа вычислений `ggml-cuda` и активации FlashAttention**:
   * При `--batch-size 2048`, `--ubatch-size 512`, `--flash-attn on`: $\approx \mathbf{0.95\text{ GiB}}$.
   * При `--ubatch-size 256`: снижается до $\approx \mathbf{0.70\text{ GiB}}$ (экономия 250 MiB).
7. **Мультимодальный проектор (`mmproj-BF16`)**:
   * $\mathbf{0.00\text{ GiB}}$ в VRAM! Флаг `--no-mmproj-offload` удерживает все 931 МБ проектора строго в системной оперативной памяти CPU хоста.

### 3.3. Суммарный базовый расход VRAM (до выделения KV-кэша)
$$\text{Static VRAM} = 18.83 + 0.84 + 0.08 + 0.35 + 0.45 + 0.95 = \mathbf{21.50\text{ GiB}}\;(\text{при } ubatch=512)$$
$$\text{Static VRAM} = \mathbf{21.25\text{ GiB}}\;(\text{при } ubatch=256)$$

## 4. Расчет максимального размера контекста без риска OOM

Бюджет, остающийся под KV-кэш и резерв безопасности:
$$\text{Доступно под KV-кэш + Резерв} = 31.60\text{ GiB} - 21.50\text{ GiB} = \mathbf{10.10\text{ GiB}}$$

Для гарантированного исключения аварийного падения из-за Out Of Memory (OOM) в production-среде необходим защитный буфер:
* Пиковые активации при глубоких рассуждениях (Thinking mode / reasoning chains);
* Вставка vision-токенов при анализе изображений (до нескольких тысяч токенов префикса);
* Динамическое масштабирование графа вычислений ggml.
* **Минимальный безопасный буфер**: $\ge \mathbf{1.50\text{ GiB}}$.
* **Рекомендуемый промышленный буфер**: $\ge \mathbf{2.00\text{ GiB}}$.

## 5. Архитектурный вывод: Определение максимального контекста

### 1. Предельный нативный контекст: **262 144 токена (256K)**
* Нативное окно модели Qwen3.8-27B составляет ровно **262 144 токена**.
* При контексте **262 144 токена** и 8-битном кэше Q8_0:
  * Размер KV-кэша составляет ровно **8.50 GiB**.
  * Суммарная занятость VRAM равна **30.00 GiB** (при `ubatch 512`) или **29.75 GiB** (при `ubatch 256`).
  * Свободный запас памяти составляет **+1.60 GiB** (+1 640 MiB) и **+1.85 GiB** соответственно.
  * Модель работает **без интерполяции RoPE (YaRN)**, обеспечивая 100% математическую точность позиционных эмбеддингов.

### 2. Рекомендуемый безопасный контекст для 24/7 Production: **240 000 токенов**
* Если на сервер регулярно отправляются пакеты с крупными изображениями (vision-токены) или выполняются параллельные тяжелые цепочки рассуждений (xhigh reasoning), установка контекста в **240 000 токенов** обеспечивает идеальный запас прочности **+2.32 GiB** (+2 375 MiB).

### 3. Почему не следует выходить за 262 144 токенов:
* Чисто физически память V100 позволила бы выделить до 280–290k токенов, но это потребовало бы искусственного растяжения частот RoPE (YaRN), что ведет к разрушению логики рассуждений, размытию внимания и деградации ответов.
* Вывод: **262 144 токена — это одновременно и максимальный нативный предел модели, и безопасный предел по VRAM для Tesla V100 32GB.**

## 6. Настройка и интеграция HauhauCS FastMTP

HauhauCS FastMTP сочетает встроенную архитектуру NextN Qwen3.8 с оптимизированным 32K draft-сайдкаром. Это обеспечивает:
* До **3.02x** ускорения Document TG относительно генерации без MTP;
* До **1.93x** ускорения Reasoning TG (рассуждения);
* На **20–35% быстрее**, чем стандартный embedded MTP;
* **100% математическое сохранение качества**: драфт генерирует гипотезы токенов, а целевая модель Q5_K_P проверяет их побитово на GPU.

### 6.1. Сборка llama.cpp с патчем HauhauCS FastMTP
```bash
git clone https://github.com/ggerganov/llama.cpp /opt/llama.cpp
cd /opt/llama.cpp
git checkout 4df29be4f4c3673f428170fda944a5b19f743bb8

curl -L -o HauhauCS-FastMTP-llama.cpp.patch \
  https://huggingface.co/HauhauCS/Qwen3.8-27B-Uncensored-HauhauCS-Aggressive-MTP-GGUF/resolve/main/HauhauCS-FastMTP-llama.cpp.patch

git apply HauhauCS-FastMTP-llama.cpp.patch

cmake -S . -B build -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j$(nproc)
```

### 6.2. Ключи запуска FastMTP в `llama-server`
```bash
--model /models/Qwen3.8-27B-Uncensored-HauhauCS-Aggressive-Q5_K_P.gguf \
--spec-draft-model /models/Qwen3.8-27B-Uncensored-HauhauCS-Aggressive-FastMTP-32K.gguf \
--spec-draft-ngl all \
--spec-type draft-mtp \
--spec-draft-n-max 3 \
--spec-draft-p-min 0
```

## 7. Размещение мультимодального проектора (`mmproj`) в CPU RAM

* Файл: `mmproj-Qwen3.8-27B-Uncensored-HauhauCS-Aggressive-BF16.gguf` (931 MB).
* Флаг принудительной выгрузки в системную RAM:
  ```bash
  --no-mmproj-offload --threads 8
  ```
* **Механика работы**:
  1. При обработке изображений процессор хоста за доли секунды выполняет Vision-кодирование в RAM хоста.
  2. Полученные эмбеддинги передаются в V100 как обычный префикс токенов.
  3. Вся текстовая генерация и рассуждения выполняются в GPU на скорости HBM2 (900 ГБ/с).
  4. Это освобождает ~1.5–2.0 GiB VRAM, позволяя безопасно развернуть KV-кэш на полный контекст 256K.
